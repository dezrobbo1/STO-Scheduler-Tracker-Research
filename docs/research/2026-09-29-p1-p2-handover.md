## Durable product/semantic boundaries to preserve

The following directions are already supported by repository authority or by a
combination of accepted repository semantics and strong cross-pass research.
Implementation should preserve them unless a later explicit decision changes
them.

### One activity-centred product, different role surfaces

Schedule and Execution are different workflow lenses over the same STO activity
identity and authoritative state. The professional desktop remains dense; the
field experience remains sparse and execution-oriented. Do not create a second
field copy of the schedule model.

The working professional-scheduler direction is a synchronized activity/WBS
table + Gantt + persistent/progressive activity inspector. That is a product
direction to implement and validate, not permission for a Gantt library to
become scheduling authority.

### Authority/state is not a flat set of equivalent tabs

Repository version kinds and research both require asymmetric treatment of
state:

- operational/authority: **Live** and **Approved forecast**;
- experimental: **Scenario**;
- reference: **Baseline** and imported/source observations;
- temporal navigation: **History/version timeline**.

The exact labels and presentation still need practitioner validation, but the
underlying authority distinctions must not be blurred.

### Accepted history is distinct from remaining future

Future recalculation, scenario work and forecast changes must not rewrite
accepted actual history. An authorised correction can supersede an accepted
fact only through its separately audited correction path while preserving prior
history.

For in-progress work, accepted actual start/history and the remaining scheduled
future are separate concepts. The UI must not make a forecast movement look
like rewritten actual history.

### Movement explanation is bounded by what the engine proves

"Why did this move?" remains a first-class planner interaction, but it must not
turn calculation lineage into an invented root-cause story.

The research hierarchy to test is:

```text
what moved
  -> proven direct placement driver, where established
  -> local driving path / relevant alternative paths
  -> related changed inputs, events or scheduling rules
  -> downstream consequence

at every level:
  cause not uniquely established, when that is the truthful answer
```

A direct driver can prove what placed an activity. It does not automatically
prove the unique historical reason a shutdown milestone moved.

### Float, driving logic, calculated criticality and operational importance are separate

Do not collapse total float, free float, driving relationships, CPM criticality,
near-critical/watch policy and human operational importance into one red
"critical" state. Human Critical communication under PL15 is also distinct from
engine-calculated criticality.

### Communication never becomes execution authority

ADR-016 and `docs/product/field-communication.md` are authoritative here.
Text, replies, reactions, photographs, annotations, delivery state and
notifications cannot mutate execution or schedule state or enter schedule
hashes. A schedule-affecting action is a separate explicit, authorised,
validated and audited execution command.

### Offline state must remain truthful

Queued is not server accepted. Accepted is not necessarily applied.
Communication acceptance is not schedule application. Media completion is
separate again. Offline creation does not preserve former authority after
permission or membership changes.

The field UI can simplify what it shows by role, but it cannot collapse these
facts into false success.

### Scenarios preserve lineage and stale state

A scenario names its base. If Live changes after the scenario was created, the
scenario becomes stale relative to current Live; it must not silently rebase or
quietly reinterpret the planner's work. Current immutable scenario lineage and
expected-version protection already point in this direction.

## Provisional UX hypotheses — validate, do not freeze

The research programme deliberately leaves these open:

- exact Schedule/Execution/Today wording and the final authority-state labels;
- exact default columns, pane sizes and inspector ordering;
- saved-view defaults and grouping/filter presets;
- materiality thresholds and near-critical thresholds;
- notification defaults and alert grouping;
- review batching/cadence and the best grouping for realistic update volumes;
- final scenario stale-state action wording;
- exact visual palette/tokens beyond non-colour-only semantic state;
- final mobile framework, local database and native boundary;
- final realtime transport and media/upload implementation;
- commercial Gantt component versus custom/grid-plus-timeline implementation.

No broad desk-research pass should be inserted merely to choose these in
advance. Build the owning P2 surface far enough to make the question real, then
test it.

## Pass 4 validation becomes part of P2 development

Pass 4 produced a validation design, not evidence that the hypotheses passed.
Its H1–H25 behavioural hypotheses remain unexecuted until representative users
and real devices perform the tasks.

Use the actual P2 product as the test instrument as usable surfaces appear:

| P2 work | Validation to perform before hardening |
|---|---|
| S7 / Schedule-facing result use | actual/history/future comprehension; movement explanation facts versus causal overclaim |
| PL4 | accepted/replayed/rejected operation understanding; truthful receipt and catch-up states |
| PL5 | real iOS/Android queued/offline/reconnect lifecycle; process termination; session/membership changes; account isolation |
| PL6 | supervisor versus planner authority; review throughput; consequential item hidden among routine updates; Approved-forecast comprehension |
| PL7 | dense planner workflow; table/Gantt/inspector comprehension; view stability during live change; stale scenario handling; recovery comparison |
| PL15 | ordinary communication versus execution; photo/annotation/media recovery; activity association; notification/deep-link behaviour; mandatory contract acceptance |

For consequence-critical behaviour, task success and wrong-authority actions
matter more than preference. Record wrong-layer actions, causal overclaims,
missed material changes, unnecessary acknowledgements, stale-scenario errors,
review misses, context loss and offline-state misunderstanding.

Pass 5 should consume genuine observations from these trials rather than become
another web/vendor survey. Pass 6 can then close the remaining UX questions and
identify what deserves durable product-contract treatment.

## View stability and attention are strong hypotheses, not yet universal rules

Professional-product evidence supports preserving planner spatial context while
live values change: selection, inspector target, scroll position, WBS expansion,
filters and Gantt zoom should not casually jump under the pointer because a
recalculation arrived. Test that behaviour against immediate automatic
reorganisation before freezing it.

Likewise, the Today/Attention direction should separate actual decisions and
execution exceptions from schedule watch and lower-priority sync/data-quality
information. Exact categories, thresholds and ordering still need realistic
role testing.
